Step 1 · Ingestion

Document chunking

Paste any document below. The pipeline splits it into overlapping chunks so no meaning is lost at chunk boundaries. Overlap ensures that sentences spanning two chunks are still findable.

💡 Why chunk? LLMs have a limited context window. Chunking lets you store large documents and retrieve only the relevant pieces at query time — not the entire document.

Step 2 · Ingestion

Vector embeddings

Each chunk is converted into a high-dimensional vector of numbers. Semantically similar text lands close together in this vector space — that's what makes search work.

🔢 Real embeddings use models like text-embedding-3-small (OpenAI) or embed-english-v3 (Cohere). Here we simulate 8-dimensional vectors based on keyword presence to illustrate the concept.

Step 3 · Ingestion

Vector database

Embeddings are stored in a vector database alongside the original chunk text. At query time, the DB performs approximate nearest-neighbour (ANN) search — orders of magnitude faster than brute-force.

🗄️ Popular options: Pinecone, Weaviate, Chroma, pgvector (Postgres), Supabase. Each entry is a (vector, text, metadata) tuple. The index is what enables fast similarity lookups.

Step 4 · Retrieval

Query embedding

Your question must be embedded using the exact same model as the chunks. This places it in the same vector space, making comparison meaningful.

⚠️ Critical constraint: If you embed chunks with model A but query with model B, the vectors live in different spaces — similarity scores will be meaningless. Always use the same model for both.

Step 5 · Retrieval

Similarity search

The query vector is compared against every stored chunk vector using cosine similarity. The highest-scoring chunks are retrieved as candidates.

📐 Cosine similarity measures the angle between two vectors (0 = unrelated, 1 = identical direction). It's robust to vector magnitude, which makes it ideal for semantic text matching.

Step 6 · Retrieval · Optional

Re-ranking

A cross-encoder model re-scores each retrieved chunk for relevance. It reads the query and each chunk together (not as separate vectors), which is slower but far more accurate.

🎯 Why re-rank? Vector search is fast but imprecise — it uses approximate nearest neighbours. Re-ranking with a cross-encoder catches cases where a chunk is semantically close but not actually relevant to your specific question.

Step 7 · Generation

Prompt composition

Retrieved chunks are injected into a structured prompt template. This is the step most diagrams skip — but it's where the actual prompt engineering happens.

🧩 What goes in the prompt: a system instruction (stay grounded), the retrieved context chunks (with source labels), and the user's question. The LLM sees only this — not the full document.

Step 8 · Generation

LLM answer

The LLM generates an answer grounded in the retrieved context. It should cite the chunks and refuse to answer if the context doesn't contain the information.

✅ Groundedness is the key RAG property: the model answers from evidence, not from parametric memory. This reduces hallucination and makes responses auditable.
